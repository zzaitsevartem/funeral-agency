# Доработка админки для нескольких администраторов

## Цель

Добавить возможность владельцу магазина создавать и отзывать учётные записи других администраторов. Этот файл — план будущей разработки; описанные возможности пока не работают.

## Как устроено сейчас

Сейчас доступ рассчитан на одну учётную запись:

- Первый администратор создаётся на скрытой странице регистрации с кодом `ADMIN_BOOTSTRAP_TOKEN`.
- Учётная запись имеет фиксированный внутренний ID `primary`.
- После её создания первичная регистрация закрывается.
- JWT выпускается только для этого ID; сервер проверяет его и активную сессию в Redis.
- В интерфейсе нет раздела управления администраторами и ролей.

Поэтому нельзя добавить второго администратора повторной регистрацией, простой сменой email или ручной вставкой строки в PostgreSQL. Нужно изменить схему, API, авторизацию, интерфейс и E2E проверки.

## Предлагаемое поведение

1. Первый зарегистрированный аккаунт становится владельцем магазина с ролью `owner`.
2. Только владелец может открыть раздел «Администраторы», создать приглашение, сменить роль и отключить аккаунт.
3. Владелец указывает email и роль. Система создаёт одноразовое приглашение на ограниченное время.
4. Приглашённый человек открывает ссылку, задаёт свой пароль и получает отдельную учётную запись.
5. Каждый человек входит под своим email и паролем. Общие пароли не используются.
6. Отключение администратора прекращает его доступ, включая уже выданные сессии.
7. Если владелец заблокирован или удалён, в системе всё равно должен оставаться хотя бы один активный владелец.

### Роли первой версии

Оставить роли простыми и понятными:

- **Владелец** — полный доступ, включая приглашение сотрудников и управление ролями.
- **Администратор** — товары, категории, заказы, платежные записи, доставка и страницы; без управления другими администраторами.

Проверять права на сервере у каждого защищённого действия. Скрытие кнопок в интерфейсе само по себе не является проверкой доступа.

## Изменения в базе данных

Подготовить миграцию Prisma для многопользовательских учётных записей:

- Сохранить текущий аккаунт и его email, чтобы владелец не потерял доступ.
- Убрать ограничение авторизации на один фиксированный ID `primary`.
- Добавить роль, состояние аккаунта (`active` / `disabled`) и даты создания/изменения.
- Уникальность email оставить; сравнивать нормализованный email в нижнем регистре.
- Добавить таблицу приглашений: нормализованный email, роль, хеш токена, срок действия, дата использования, кто создал и дата отзыва.
- Не сохранять пароль или исходный токен приглашения открытым текстом.
- Добавить журнал событий для создания/отзыва приглашения, активации, смены роли и блокировки аккаунта.

Миграция должна быть добавочной и сохранять существующий аккаунт. Не удалять и не пересоздавать рабочие данные. Подготовить способ резервного копирования и отката схемы до запуска миграции на постоянной базе.

## Защищённый сценарий приглашения

- Генерировать токен приглашения криптографически стойким генератором случайных чисел.
- Хранить в БД только криптографический хеш токена; показать исходный токен только в ссылке-приглашении.
- Срок действия — ограниченный (например, 24 часа); владелец может отозвать приглашение раньше.
- Приглашение действует для конкретного email и роли, используется один раз.
- GET страницы приглашения не должен активировать или погашать его: почтовые сканеры часто сами открывают ссылки. Погашать токен только при явном POST после ввода пароля.
- Ограничить частоту выдачи и проверки приглашений. Ответы не должны раскрывать, зарегистрирован ли произвольный email.
- Не включать токен в access-логи, аналитику, сторонние ресурсы или Referer. Для страницы приглашения установить `noindex` и строгую политику `Referrer-Policy: no-referrer`.
- После успешной активации токен немедленно становится недействительным; повторное использование отклоняется.
- Если почта не настроена, для первой версии показать владельцу ссылку один раз с действием «Скопировать приглашение». В документации явно объяснить, что ссылку надо передать лично и не публиковать. Позже подключить почтового провайдера, не меняя модель безопасности.

## Авторизация и сессии

- JWT должен содержать ID конкретного администратора, а не фиксированный ID владельца.
- При каждом запросе проверять подпись, алгоритм, срок действия и обязательные claims; затем загрузить аккаунт из PostgreSQL и проверить его состояние и роль.
- Redis allowlist сессий связывать и с JWT `jti`, и с ID аккаунта. Проверять запись на каждом admin API запросе.
- Выход удаляет запись сессии из Redis. Блокировка аккаунта должна отзывать все его активные сессии либо обеспечивать их немедленный отказ при следующем запросе.
- При Redis недоступности доступ закрывать.
- Сохранить защищённую HttpOnly cookie, CSRF/Origin проверки для изменяющих запросов, ограничения попыток входа, хеширование паролей и нейтральные ошибки входа.
- Логировать события безопасности без паролей, JWT, cookie и токенов приглашения.

## Изменения API

Добавить защищённые маршруты управления администраторами. Названия можно подогнать под текущую структуру API, но права должны быть такими:

| Действие | Кто может |
|---|---|
| Список и просмотр администраторов | владелец |
| Создать приглашение | владелец |
| Отозвать неиспользованное приглашение | владелец |
| Сменить роль | владелец |
| Отключить/включить администратора | владелец |
| Принять действующее приглашение и задать пароль | только предъявитель подходящего одноразового токена |
| Обычная работа с товарами и заказами | активный владелец или администратор |

Проверка роли должна находиться в backend middleware/обработчиках, рядом с выполнением действия. Клиентский React-admin UI не может быть единственным местом проверки.

## Изменения интерфейса

Добавить пункт «Администраторы» в левое меню. Для владельца показать:

- список email, роль, состояние и дату создания;
- форму приглашения с email и ролью;
- копирование ссылки-приглашения один раз;
- срок действия, состояние и отзыв приглашений;
- смену роли и отключение аккаунта с подтверждением.

Для администратора без роли владельца скрыть управление аккаунтами, но всё равно запретить эти API на сервере.

Приглашённому показать отдельную страницу принятия приглашения: email (неизменяемый), создание и повтор пароля, понятные сообщения об истёкшем или отозванном приглашении. Не использовать текущую первичную регистрацию с bootstrap-кодом для выдачи обычных приглашений.

Показывать в шапке вошедшего пользователя и его роль. Добавить заметный выход. Сохранить текущую страницу входа и скрытый адрес; он не заменяет авторизацию.

## Порядок реализации

1. Сделать резервную копию локальной базы и проверить миграцию на отдельной тестовой базе.
2. Добавить миграцию, сохранить владельца `primary`, проверить, что он может войти.
3. Перевести выпуск и проверку JWT на ID пользователя; проверить отзыв сессии.
4. Добавить backend-проверки ролей и защищённые маршруты управления администраторами.
5. Добавить UI списка и приглашения, затем страницу принятия приглашения.
6. Реализовать блокировку аккаунтов, отзыв сессий и журнал аудита.
7. Выполнить E2E проверки ниже на отдельном Compose окружении.
8. Подготовить staging, проверить приглашение двумя разными браузерами/профилями и только после этого планировать перенос миграции на постоянную базу.

Не хранить настоящий production `.env` в Git и не печатать его значения в отчётах.

## Обязательные E2E проверки

- Текущий владелец после миграции может войти со старым email и паролем.
- Гость, неавторизованный пользователь и аккаунт без роли владельца не могут читать или изменять список пользователей и приглашения.
- Владелец создаёт приглашение; в БД хранится хеш токена, а не его исходное значение.
- Неподходящий email, неверный, истёкший, отозванный и повторно использованный токены отклоняются.
- GET страницы по ссылке не погашает приглашение; успешный POST с паролем делает это ровно один раз.
- Приглашение доступно только адресу email, для которого создано.
- Приглашённый входит и получает только свои права; прямой запрос к API владельца возвращает запрет.
- Отключённый администратор теряет доступ сразу, в том числе со старой cookie/JWT.
- Выход отзывает сессию; повтор старого JWT не работает.
- Нельзя отключить последнего активного владельца или случайно снять с него роль без назначения другого владельца.
- Ограничения частоты, журналирование без секретов, CSRF/Origin и ошибки Redis проверены.

## Критерий готовности

Второй человек получает личную одноразовую ссылку, задаёт собственный пароль, входит со своим email и может выполнять только разрешённые действия. Владелец может отозвать его доступ без изменения общего пароля. Сценарии подтверждены E2E тестами.
